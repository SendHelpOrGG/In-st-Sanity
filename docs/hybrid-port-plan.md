# In-st-Sanity — Hybrid Desktop Port Plan

**Goal:** ship the attached `index.html` (the In[st]Sanity Instagram post saver) as a native
Windows desktop app inside this MAUI project — same UI, same animations, same sounds, same behaviour.

**Decisions taken (from the kick-off Q&A):**

| Decision | Choice |
| --- | --- |
| Approach | **Hybrid** — native MAUI host + the existing web app running inside WebView2 |
| Fidelity target | **100%** — the web layer runs unmodified, so nothing has to be approximated |
| Instagram fetching | **Direct HTTP from C#** — no `microlink.io` / `r.jina.ai` / `wsrv.nl` proxies |

Subsystems present: boot/loading screens, library grid with pagination/search/sort/filter, card +
detail + photo-fullsize views, multi-select and downloads, drag-and-drop JSON import, "save from
URL" tab, tabbed settings, 12-theme picker, background image/GIF with crop modal, ~40 behaviour
toggles, toasts, a WebAudio **sound engine** (`Convolver` reverb, `WaveShaper` distortion,
`BiquadFilter`, oscillators, noise buffers), and an animated SVG character ("Imp") built by
**31 procedural art functions** with eye-tracking, blink, six-expression loop, click-dodge and
squash bursts.

### 1.1 The discovery that shapes this plan

The app is **not standalone**. It is a *client for a local backend*, and it degrades when that
backend is missing:

```js
function isLocalBackendOrigin(){ … window.location.port==='8000' || hostname==='localhost' … }
function getApiUrls(path){ if(isLocalBackendOrigin()) return [path];
  const list=[]; if(protocol.startsWith('http') && Date.now()>localOriginDeadUntil) list.push(path);
  if(SERVER_API_BASE && Date.now()>serverBaseDeadUntil) list.push(SERVER_API_BASE+path); return list }
const SERVER_API_BASE="https://1ddc5d8b8d7a67.lhr.life"   // ← dead dev tunnel
```

- It calls a backend on **port 8000** with 10 `/api/*` routes (§4).
- When the backend is absent it falls back to third-party scrapers (`microlink.io`, `r.jina.ai`)
  and an image proxy (`wsrv.nl`) — which is also how the author ran it in a browser.
- Its "built-in Instagram browser" is **not** an iframe: `POST /api/browser/action` and
  `GET /api/browser/state?screenshot=1` mean the backend ran a **headless browser** and shipped
  screenshots to the UI, which renders them.

**Consequence:** a faithful desktop port is mostly *native work* — the MAUI app must **become that
backend**. The web layer then needs almost no changes (§6), which is exactly why fidelity is 100%.

```
┌──────────────────────────────────────────────────────────────────────────────────┐
│ In-st-Sanity.exe  (net10.0-windows10.0.19041.0, MAUI, unpackaged)               │
│                                                                                  │
│  ┌─────────────────────────┐        ┌─────────────────────────────────────────┐  │
│  │  MAUI Shell (native)    │        │  WebView2  ← the whole web app          │  │
│  │  • window + dark chrome │        │    http://127.0.0.1:8000/               │  │
│  │  • single instance      │        │    (unmodified HTML/CSS/JS)             │  │
│  │  • tray / taskbar       │◄──────►│    • 12 themes, keyframes, sticker      │  │
│  │  • dialogs & pickers    │  same  │    • WebAudio sound engine              │  │
│  │  • theme (AppTheme.Dark)│ origin │    • localStorage + IndexedDB           │  │
│  └─────────────────────────┘        └───────────────┬─────────────────────────┘  │
│                                                     │ fetch('/api/…')            │
│  ┌──────────────────────────────────────────────────▼─────────────────────────┐  │
│  │  Loopback host  127.0.0.1:8000  (TcpListener micro-server, in-process)     │  │
│  │    GET  /                        → wwwroot/index.html + assets             │  │
│  │    /api/resolve-post|batch|owners|cached-posts   → Instagram (direct HTTP) │  │
│  │    /api/image|download-photo|download-selected   → media + file writing    │  │
│  │    /api/save-imported-list                       → %LOCALAPPDATA% store    │  │
│  │    /api/browser/action|state                     → hidden WebView2 session │  │
│  └──────────────────────────────────────────────────┬─────────────────────────┘  │
│                                                     │                          │
│  ┌──────────────────────────┐   cookies    ┌────────▼───────────────────────┐   │
│  │ HttpClient + CookieJar   │◄─────────────│  Hidden WebView2 = IG session  │   │
│  │ (direct, no proxies)     │              │  login, cookies, screenshots   │   │
│  └──────────────────────────┘              └────────────────────────────────┘   │
└──────────────────────────────────────────────────────────────────────────────────┘
```

Five moving parts:

1. **Native MAUI host** — window, dark title bar, app icon, single-instance guard, user-data-folder
   pinning, external-link handling, dev tools in Debug, zip/MSIX packaging.
2. **Loopback host on `127.0.0.1:8000`** — serves `wwwroot` statics *and* `/api/*`.
   Same origin ⇒ **no CORS anywhere**, `localStorage`/`IndexedDB`/`WebAudio`/`navigator.clipboard`
   all work (loopback counts as a secure context), and `isLocalBackendOrigin()` returns `true`,
   so the web app takes its intended "local backend" fast path.
3. **WebView2 hosting the web app** — Chromium, so glass (`backdrop-filter`), gradients,
   `clip-path`, keyframes, SVG animation and WebAudio all behave exactly as in the browser.
4. **Hidden WebView2 as the Instagram session** — real login, real cookies, and
   `CoreWebView2.CapturePreviewAsync` provides the screenshots the legacy `/api/browser/*`
   contract expects. This is also where "direct HTTP" gets its teeth: session cookies are mirrored
   into the `HttpClient` cookie jar, so C# fetches see the same logged-in view as the browser.
5. **Native file services** — folder/file pickers, a download sink (`WebView2.DownloadStarting`),
   media writing, and the persisted "imported list" store.

### 2.1 Why a loopback server instead of a JS bridge

| Option | JS changes | Same-origin API | Notes |
| --- | --- | --- | --- |
| **Loopback host on :8000** ✅ | **none** | yes | matches the app's own backend contract, incl. `isLocalBackendOrigin()`; needs a free port |
| `HybridWebView` + virtual host + `fetch` shim | ~40-line shim | no (shim only) | no port, but `isLocalBackendOrigin()` can't be satisfied and every API call must be intercepted |
| `HybridWebView` + C# bridge for everything | rewrite call sites | no | most invasive; loses the app's own fallback logic |

The loopback option wins because the web app was *written* for it: downloads-to-a-folder, image
proxying and browser screenshots are all server-side concepts already.

## 4. API contract to implement

Every route the web app calls, as the JS actually uses it:

| Route | Method | Request | Response fields the JS reads | C# implementation |
| --- | --- | --- | --- | --- |
| `/api/resolve-post` | GET | `?url=<postUrl>` | `{ok, fullResolved, shortcode, owner, likes, caption, media[]}` → `applyResolvedPostData` | Direct `HttpClient`: fetch `/p/{code}/embed/captioned/`, parse JSON blobs + `og:` tags, fall back to the `/p/{code}/?__a=1&__d=dis`-style endpoints; cookie jar attached |
| `/api/resolve-batch` | GET | `?urls=csv` (chunks of 5) | `{byShortcode:{sc:{…}}, posts:[{shortcode,…}]}` | Parallel resolve with concurrency cap (mirror `MAX_CONCURRENT_COVER_RESOLVES=2`) |
| `/api/resolve-owners` | GET | `?urls=csv` | `{byShortcode, posts:[…]}` (account name only) | Lightweight: single embed fetch per post, owner only |
| `/api/cached-posts` | GET | — | cached post records | JSON file in `%LOCALAPPDATA%\InStSanity\cache` |
| `/api/image` | GET | `?url=<mediaUrl>` | image bytes | Streaming proxy with `Referer`/UA headers so Instagram CDN links resolve; caches to disk |
| `/api/download-photo` | GET | `?url=<mediaUrl>` | file bytes | Same as `/api/image` with `Content-Disposition: attachment` |
| `/api/download-selected` | POST | `{folder, items[]}` | `{ok, files:[{filename,…}]}` | **Native**: expand `~/…`, create folder, download each item (HTTP or reuse cache), write files, return the written paths. Folder picker offered when the path is invalid |
| `/api/save-imported-list` | POST | imported list JSON | ok | Atomic write to the app data store (replaces browser-only persistence) |
| `/api/browser/action` | POST | `{action:'navigate'\|'login'\|…, url, username, password}` | browser state (§ below) | Drives the **hidden WebView2** |
| `/api/browser/state` | GET | `?screenshot=1` | `{loggedIn, username, url, screenshot}` | `loggedIn`/`username`/`url` from the hidden WebView2 + `CapturePreviewAsync` → base64 PNG for `screenshot` |

Notes for the implementer:

- **Port 8000** is what `isLocalBackendOrigin()` checks. Bind it by default; if the port is taken,
  probe for the next free port and serve from there (the app still works — `getApiUrls()` pushes the
  relative path for any `http(s)` origin — but the 8000 fast path is preferable).
- The micro-server needs: MIME map (html/js/css/png/jpg/webp/gif/mp4/woff2), `Content-Length`,
  **`Range` support (§206)** because the app plays video, cache headers for `/assets`, and a
  `/__health` endpoint for the Phase-5 smoke test.
- Timeouts must match the JS expectations (12–30 s) or it will treat the backend as dead
  (`localOriginDeadUntil` back-off).

## 7. Phases

Each phase is independently buildable and testable on your Windows machine, and shippable on its
own. Sizes are relative effort, not calendar time.

### Phase 1 — Native host boots the app · `M`
- `MainPage` hosts a `WebView`; loopback micro-server serves `wwwroot` statics with ranges + MIME.
- Window: dark chrome, 1280×820 default, min size, title, icon; single-instance guard.
- WebView2 user-data folder pinned to `%LOCALAPPDATA%\InStSanity\WebView2` (keeps localStorage/IndexedDB).
- `NewWindowRequested` → system browser; Debug builds enable dev tools.
- **Done when:** `dotnet run` opens the window and the full web app boots, themes switch, the
  sticker animates and sounds play — with no network access to any third-party proxy.

### Phase 2 — Files & downloads · `M`
- `/api/image`, `/api/download-photo`, `/api/download-selected`, `/api/save-imported-list`, `/api/cached-posts`.
- Native folder picker + path expansion (`~/Pictures/Instagram`), atomic JSON writes, disk cache.
- `DownloadStarting` sink for the one `<a download>` path; failures toast in the UI as today.
- **Done when:** selecting posts and hitting Download writes real image files to the chosen folder
  and the UI reports the same per-file results it used to get from the backend.

### Phase 3 — Instagram session & resolution · `L`
- Hidden WebView2 login (`/api/browser/action|state`, `CapturePreviewAsync` screenshots).
- Cookie mirror WebView2 → `CookieContainer` → `HttpClient`.
- `/api/resolve-post`, `/api/resolve-batch`, `/api/resolve-owners` with concurrency caps,
  disk cache, and graceful `ok:false` so the app's own source badges/status notes still apply.
- **Done when:** the in-app browser modal logs in, resolution fills owner/media/metadata for a page
  of posts, and blocked/failed posts degrade exactly as the web app already handles them.

### Phase 4 — Polish & distribution · `M`
- Externalise base64 assets (§6.3); boot/splash parity with the web app's loading screens.
- Native JSON import/export dialogs as an alternative to drag-and-drop; "open containing folder".
- Unpackaged publish + optional MSIX with the Evergreen WebView2 prerequisite; app icon already in place.
- Window state persistence, taskbar/jump-list niceties.
- **Done when:** a released build runs on a clean Windows machine with no dev tooling.

### Phase 5 — Verification & CI · `S`
- GitHub Actions on `windows-latest`: `dotnet workload install maui-windows`, build, publish artifact.
- Smoke test: launch the exe headless-ish, hit `/__health`, assert the WebView loaded and JS ran
  (the app posts a ready beacon), capture a screenshot of the window for the PR.
- Manual checklist per phase in `docs/`.

## 8. Verification strategy (important)

I cannot compile Windows MAUI targets in this Linux sandbox — no .NET SDK here. Three safeguards:

1. **CI is the compiler.** A `windows-latest` workflow builds every push and publishs the artifact;
   I can dispatch runs and read logs, so MAUI code lands verified instead of "should compile".
2. **Phase-sized changes.** Each phase is small enough that a first build failure is cheap to fix,
   rather than facing thousands of lines of unverified code at once.
3. **Runtime smoke test** (§Phase 5) proves the web app actually booted inside WebView2, which
   static checking can never prove.

## 9. Risks & mitigations

| Risk | Impact | Mitigation |
| --- | --- | --- |
| Instagram blocks unauthenticated scraping | Resolution partially fails | Session cookies from the hidden WebView2; disk cache; `ok:false` → app's existing badges/degraded states; JSON import stays the reliable path |
| WebView2 Runtime missing on target machine | App won't render | Evergreen runtime ships with Windows 11 / most Windows 10; MSIX declares the dependency; add a friendly first-run check |
| Port 8000 occupied | API calls fail | Probe free port, serve there (relative paths still resolve); surface the chosen port in logs |
| Third-party dependency on Chromium behaviour | — | none: the web layer already targets Chromium |
| 2.85 MB single-file parse on startup | Slow first paint | Phase 4 asset externalisation; WebView2 caches statics |
| localStorage/IndexedDB lost between runs | Settings/reset on every launch | Pinned user-data folder (Phase 1) |
| WebAudio blocked by autoplay policy | No UI sounds | Relax policy via WebView2 `AdditionalBrowserArguments`, plus the boot screen already requires a click |
| Web layer is a 5,369-line JS blob | Hard to maintain/debug | Out of scope; dev tools + source map optional in Phase 1 |
| Antivirus/SmartScreen on unpackaged exe | Friction to install | MSIX path in Phase 4 |
